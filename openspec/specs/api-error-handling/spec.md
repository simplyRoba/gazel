## Purpose

Consistent API error behavior: a uniform JSON response shape, error-category-to-HTTP-status mapping, safe handling of persistence failures, request-body validation, and stable error codes usable for localization.

## Requirements

### Requirement: Consistent JSON error responses

Errors generated by Gazel application request processing SHALL have a JSON body with `code` and `message` fields. The `code` SHALL be a static string identifier and the `message` SHALL be a human-readable English fallback. Framework-generated rejections outside application error handling, including malformed path or query extraction and unmatched routes, are outside this requirement.

#### Scenario: Application error response format
- **WHEN** Gazel application request processing returns an error response
- **THEN** the response body SHALL be JSON with the shape `{ "code": "<ERROR_CODE>", "message": "<human-readable message>" }`
- **AND** the `Content-Type` header SHALL be `application/json`

### Requirement: Error category to HTTP status mapping

Application-generated errors SHALL map each error category to the appropriate HTTP status code.

#### Scenario: Resource not found
- **WHEN** an application error indicates that a requested resource was not found
- **THEN** the HTTP status SHALL be `404 Not Found`

#### Scenario: Validation failure
- **WHEN** an application error indicates that semantically valid input failed validation
- **THEN** the HTTP status SHALL be `422 Unprocessable Entity`

#### Scenario: Resource conflict
- **WHEN** an application error indicates a conflict with existing state
- **THEN** the HTTP status SHALL be `409 Conflict`

#### Scenario: Invalid request
- **WHEN** an application error indicates that the request cannot be parsed or processed as submitted
- **THEN** the HTTP status SHALL be `400 Bad Request`

#### Scenario: Internal failure
- **WHEN** an application error indicates an unexpected internal failure
- **THEN** the HTTP status SHALL be `500 Internal Server Error`

### Requirement: Safe persistence error handling

Persistence failures SHALL be recorded with diagnostic details while returning a generic application error that does not expose those details to the client.

#### Scenario: Persistence operation fails
- **WHEN** a persistence operation fails unexpectedly
- **THEN** the underlying failure SHALL be logged at error severity
- **AND** the response SHALL be `500 Internal Server Error`
- **AND** the response code SHALL be `INTERNAL_ERROR`
- **AND** underlying persistence details SHALL NOT appear in the response

### Requirement: Invalid JSON request bodies

API endpoints that accept JSON request bodies SHALL return the standard application error shape when a body is malformed or does not match the required schema.

#### Scenario: Valid JSON body
- **WHEN** an API endpoint receives a valid JSON body matching its required schema
- **THEN** request processing SHALL continue normally

#### Scenario: Malformed JSON body
- **WHEN** an API endpoint receives malformed JSON
- **THEN** the response SHALL be `400 Bad Request`
- **AND** the body SHALL be `{ "code": "INVALID_REQUEST_BODY", "message": "..." }`

#### Scenario: Missing required fields
- **WHEN** an API endpoint receives valid JSON that omits fields required by its request schema
- **THEN** the response SHALL be `400 Bad Request`
- **AND** the body SHALL be `{ "code": "INVALID_REQUEST_BODY", "message": "..." }`

### Requirement: Vehicle error codes

Vehicle-specific error codes SHALL have stable human-readable English fallback messages.

#### Scenario: Vehicle error code messages
- **WHEN** an error response uses a vehicle error code
- **THEN** the following mappings SHALL apply:
- **AND** `VEHICLE_NOT_FOUND` SHALL map to `"Vehicle not found."`
- **AND** `VEHICLE_NAME_REQUIRED` SHALL map to `"Vehicle name is required."`
- **AND** `VEHICLE_INVALID_FUEL_TYPE` SHALL map to `"Invalid fuel type."`
- **AND** `VEHICLE_INVALID_YEAR` SHALL map to `"Invalid year."`
- **AND** `VEHICLE_HAS_FILLUPS` SHALL map to `"Cannot delete vehicle with existing fill-ups."`

### Requirement: Fill-up error codes

Fill-up-specific error codes SHALL have stable human-readable English fallback messages.

#### Scenario: Fill-up error code messages
- **WHEN** an error response uses a fill-up error code
- **THEN** the following mappings SHALL apply:
- **AND** `FILLUP_NOT_FOUND` SHALL map to `"Fill-up not found."`
- **AND** `FILLUP_DATE_REQUIRED` SHALL map to `"Fill-up date is required."`
- **AND** `FILLUP_FUEL_AMOUNT_REQUIRED` SHALL map to `"Fuel amount is required."`
- **AND** `FILLUP_INVALID_FUEL_AMOUNT` SHALL map to `"Fuel amount must be greater than zero."`
- **AND** `FILLUP_INVALID_ODOMETER` SHALL map to `"Odometer reading must not be less than the previous reading."`
- **AND** `FILLUP_INVALID_COST` SHALL map to `"Cost must not be negative."`

### Requirement: Error codes as stable localization keys

The `code` field in API error responses SHALL serve as the stable identifier for frontend localization. The `message` field SHALL remain an English-language fallback only. The frontend SHALL display a localized message for known codes rather than displaying the fallback directly.

#### Scenario: Error code has a localized message

- **WHEN** the backend returns `{ "code": "VEHICLE_NOT_FOUND", "message": "Vehicle not found." }`
- **AND** the active locale defines a message for `VEHICLE_NOT_FOUND`
- **THEN** the frontend SHALL display the localized message

#### Scenario: Error code has no localized message

- **WHEN** an error response uses a code with no message defined for the active locale
- **THEN** the frontend SHALL display the response's `message` fallback

#### Scenario: Supported locales cover API errors

- **WHEN** an API error code is used by the application
- **THEN** every supported locale SHALL define a corresponding localized message

### Requirement: Authentication failures use the standard API error contract

A missing, invalid, or expired Gazel session for `/api` and `/api/*` SHALL produce a standard application-generated JSON error response and SHALL NOT produce a browser redirect.

#### Scenario: Unauthenticated API request
- **WHEN** a request without a valid Gazel session targets `/api` or any `/api/*` path
- **THEN** the response SHALL be `401 Unauthorized`
- **AND** the JSON error code SHALL be `AUTHENTICATION_REQUIRED`
- **AND** the fallback message SHALL be `Authentication is required.`
- **AND** no `Location` header SHALL be present
